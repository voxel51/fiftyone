# Yarn patches

This directory contains [Yarn patch](https://yarnpkg.com/features/patching)
files — small, vendored diffs applied on top of specific npm packages at
install time. They exist to backport upstream bug fixes that we need **now**
but that haven't shipped in a release yet. Every patch here should be
temporary: each one must reference the upstream PR/commit that makes it
obsolete, and should be deleted as soon as a release containing that fix is
adopted.

## How patches are wired up

A patch is only active if a `package.json` dependency (or a root `resolutions`
entry) references it, e.g. in `packages/looker-3d/package.json` and
`packages/multimodal/package.json`:

```json
"three": "patch:three@npm%3A0.185.1#~/.yarn/patches/three-npm-0.185.1-e07195d8b4.patch"
```

The `~/` prefix means "relative to the workspace root" (`app/`), not your home
directory. The hash in the filename is generated by Yarn — don't hand-edit it.

## Current patches

### `@mcap-core-npm-2.2.1-fdbe7fc61b.patch`

**What it fixes:** `McapIndexedReader` parses `Chunk.records` into a fresh
`Uint8Array` before calling a decompression handler. That copy has no stable
relationship to the source `IReadable`, so consumers cannot safely share
decompressed chunks across refetched reads. This patch adds an optional
`IReadable.sourceIdentityForBytes()` hook that runs on the original read
buffer, plus an optional third handler argument carrying that source/version
identity, the indexed chunk's start/length, exact compressed payload range,
compression, and uncompressed size. Existing readables and two-argument
handlers remain compatible.

**Upstream status:** no upstream issue or PR exists yet. The limitation was
reconfirmed on upstream `main` at
[foxglove/mcap@95d0673](https://github.com/foxglove/mcap/blob/95d0673564eac0b27fd9a8616083fdd47c4c2ec7/typescript/core/src/McapIndexedReader.ts#L574-L588),
where the handler still receives only the copied buffer and uncompressed size.
An upstream equivalent of `ChunkDecompressionContext` is still required.

**Files patched:** TypeScript source, ESM/CJS runtime builds, and ESM/CJS type
declarations for `McapIndexedReader` and `DecompressHandlers`.

**When to drop it:** after an `@mcap/core` release exposes equivalent stable
indexed-chunk context to decompression handlers. Replace the `patch:`
dependency with its normal semver range, run `yarn install`, and keep the real
`McapIndexedReader` integration test as the upgrade guard.

### `three-npm-0.185.1-e07195d8b4.patch`

**What it fixes:** WebGPU renderer bug where disposing a geometry deletes the
GPU buffers of the **live** geometry (and leaks its own) if the render object
was switched to a different geometry before the dispose. Symptoms: broken or
disappearing meshes/point clouds after geometry swaps, WebGPU validation errors
about destroyed buffers.

**Upstream status:**
[three.js PR #33939](https://github.com/mrdoob/three.js/pull/33939), merged to
`dev` as `4e369cb`, **not yet in any release as of r185**.

**Files patched:** the fix is applied in three places because three ships both
sources and prebuilt bundles, and consumers may resolve either:

- `src/renderers/common/Geometries.js` (source of truth)
- `build/three.webgpu.js` (what `import ... from "three/webgpu"` resolves to)
- `build/three.webgpu.nodes.js` (same code, nodes build)

**When to drop it:** on the next `three` upgrade, check whether the release
includes #33939 (look at `src/renderers/common/Geometries.js` in the new
version — the buggy line is
`const geometryAttributes = renderObject.getAttributes();` inside
`initGeometry`'s `onDispose`). If the fix shipped, remove the patch file, drop
the `patch:` references from the two package.jsons in favor of a plain semver
range, and run `yarn install`.

**History:** an earlier version of this patch
(`three-npm-0.182.0-018c941206.patch`, deleted) also carried backports of
upstream #32700 (attribute id vs version in `RenderObject`) and #33160
(`nodeBuilderState` undefined crash in `Nodes`/`NodeManager`). Both shipped by
r185, so only the dispose fix was re-ported. If you're debugging a regression
after a three upgrade, that old patch (in git history) is a good list of the
WebGPU disposal bugs we've been bitten by before.

## How to modify or re-create a patch (e.g. after a three upgrade)

Do **not** edit the `.patch` files by hand — regenerate them so contexts and
hashes stay correct:

1. Bump the package version in the consuming package.jsons to a plain semver
   range (e.g. `"three": "^0.186.0"`) and `yarn install`.
2. Check whether the upstream fix shipped (see "When to drop it" above). If it
   did, delete the patch and this section — you're done.
3. If not, run `yarn patch three@npm:<exact-version>`. Yarn extracts the
   package to a temp directory and prints its path.
4. Apply the fix to the extracted files (all three files listed above — the
   prebuilt bundles too, not just `src/`). Keep the
   `// TEMPORARY vendored fix — upstream PR #...` comments so the next person
   knows what to check.
5. Run `yarn patch-commit -s <temp-dir>`. This writes the new patch file here
   and rewires the `patch:` references in the consuming package.jsons.
6. **Check the diff of the root `package.json`:** `yarn patch-commit -s` may
   add a `resolutions` entry that force-upgrades _other_ consumers of the
   package (e.g. `stats-gl`'s transitive `three@^0.170.0`) onto the patched
   version. Revert that unless you actually intend to dedupe them.
7. Delete the old patch file, `yarn install`, and verify the fix landed in
   `node_modules`:
   `grep "upstream PR" node_modules/three/build/three.webgpu.js`.

## Notes for agents

- Patches only affect installs; if `node_modules` predates a patch change, run
  `yarn install` before concluding a fix is or isn't present.
- The `.patch` files are line-exact: they will fail to apply on any other
  package version. An upgrade always requires the regeneration flow above.
- If a WebGPU rendering regression appears after a `three` upgrade, first
  verify the patch is still referenced in the consuming package.jsons — an
  upgrade that replaces the `patch:` protocol with a plain semver range
  silently drops the fix.
